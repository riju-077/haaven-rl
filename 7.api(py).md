# Step 7: api/main.py, the waiter

**In short:** the API reads `artifacts/results.json` and hands it to whoever asks (later, the dashboard). It **never** trains or calculates anything.

How to run (from the project folder):
```
uv run fastapi dev api/main.py
```
Then open in the browser:
- `http://127.0.0.1:8000/summary` to see the numbers
- `http://127.0.0.1:8000/docs` for a free test page where you can click and try each endpoint

| Part | Restaurant | Job |

The waiter never cooks. If the fridge is empty, the waiter says so instead of breaking down.

## 1. What an API is (my "supersonic" question)

**My first thought:** when the user clicks a "Summary" button in the UI, the dict travels from the server to the UI and shows on screen at supersonic speed. That's what an API is.

**The flow is correct:**
1. The user clicks "Summary". The UI sends a request: `GET /summary`
2. The server reads `results.json` and replies with the data
3. The UI turns the data into numbers or a chart on the screen

**The correction:** speed is **not** what makes it an API.
- An API is the **agreed way to ask and answer**, a fixed menu.
- The UI knows that asking `/summary` **always** returns data shaped like `{"agent": ..., "baseline": ...}`. That fixed agreement (the "contract") is the API.
- Example: a waiter isn't defined by being fast. A waiter is defined by the menu. You order "item 3" and you always get item 3. A slow waiter is still a waiter.
- Here it's fast only because the server and the browser are on the same computer.

**Why the instinct is still good (system design):** speed matters a lot in real systems. It's called **latency**, the time from request to answer. Real systems care about it, e.g. "the page must load in under 200 ms." Two easy ways we already keep it low:
- `/summary` sends only the small numbers, not the 482-day `daily` list. Less data means a faster reply.
- The waiter only *reads* a ready-made file. It never runs training while the user waits.

So: **API = the contract (what you can ask and what you get back). Speed = latency, an important *quality* of the API, but not its definition.**

**Small detail:** the data doesn't travel as a Python dict. It goes as **JSON text** over HTTP. Python turns the dict into JSON text, and the browser's JavaScript turns the text back into data. That's why any language can understand it.

## 2. The code, piece by piece

| Piece | What it does | Example |
|---|---|---|
| `RESULTS_PATH` | where the fridge is: `artifacts/results.json`, found relative to this file | works even if you start the server from another folder |
| `app = FastAPI(...)` | creates the waiter | |
| `CORSMiddleware` | allows a webpage on another address to read our answers | dashboard at `localhost:5173` asks the API at `localhost:8000`. Without this, the browser blocks it |
| `load_results()` | opens the file **fresh on every request** | re-run the backtest and the new numbers show up without restarting the server |
| missing file | returns error **404** with a helpful message instead of crashing | "results.json not found. Run: uv run python -m scripts.backtest" |

**The menu (endpoints):**

| Endpoint | Returns | Used for |
|---|---|---|
| `GET /health` | `{"status": "ok"}` | a quick check that the server is alive |
| `GET /results` | the whole file (summary, 482 daily values, agent_actions) | charts in the dashboard |
| `GET /summary` | only `test_period`, `agent`, `baseline` | the number cards (final value, drawdown, Sharpe) |

**`@app.get("/summary")`** is a "decorator". It tells FastAPI: "when someone asks for `/summary`, run the function below and send back what it returns."

---

## 3. Words to remember

- **Endpoint:** one item on the menu, e.g. `/summary`.
- **GET:** a request that only *reads* (asks for data, changes nothing).
- **JSON:** the text format the data travels in.
- **404:** the standard code for "not found". 200 means "OK".
- **CORS:** a browser safety rule. A page may only read another address's data if that server allows it.
- **Latency:** how long the answer takes to arrive.
