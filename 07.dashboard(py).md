# Step 8: frontend/index.html, the dashboard (the customer)

**In short:** a webpage that asks the API for data and draws it. It only does small, quick maths on that data (the period buttons, section 6). It never trains or runs the agent.

How to run (from the project folder):
```
uv run fastapi dev api/main.py
```
Then open **`http://127.0.0.1:8000/`**. One command runs both the API and the dashboard.

---

## 0. Where it fits (restaurant analogy)

| Part | Restaurant | Job |
|---|---|---|
| artifacts/results.json | the fridge | the ready-made results |
| api/main.py | the waiter | brings data when asked |
| **frontend/index.html** | **the customer at the table** | **orders (`/summary`, `/results`) and enjoys the food (shows it on screen)** |

New this step: the waiter now also hands over the **menu card** itself. `GET /` returns the dashboard page.

---

## 1. Why this recommendation (plain HTML + JavaScript + Chart.js, served by FastAPI)

**The choice:** one file, `frontend/index.html`, written in plain HTML/CSS/JavaScript. Charts come from **Chart.js**, loaded from the internet (a CDN). FastAPI serves the page at `/`.

**Other options I didn't pick:**

| Option | What it is | Why not here |
|---|---|---|
| React / Vue | a big frontend framework | needs Node.js, npm and a build step: hundreds of files for one page |
| Streamlit | a Python dashboard tool | quick, but it skips the API completely, so the "waiter" step would be pointless |
| Plain HTML + Chart.js ✅ | one file, no build | see the advantages below |

**Advantages of the choice:**
1. **Nothing to install.** No Node, no npm. Chart.js comes from a link (`<script src="...chart.umd.min.js">`).
2. **One file.** Easy to read top to bottom, and easy to explain in an interview.
3. **One command runs everything.** FastAPI serves both the data *and* the page. Example: open `127.0.0.1:8000/` and done, no second server.
4. **Same address, so no CORS trouble.** The page and the API both live at `127.0.0.1:8000`, so the browser doesn't block anything. (The CORS setting from step 7 is still there in case the page is ever hosted somewhere else.)
5. **It shows real system design.** The frontend and backend are cleanly separated and only talk through the API contract (`/summary`, `/results`). Swapping in React later wouldn't change the API at all.
6. **Right size for the job.** It's a read-only page with 4 cards and 2 charts, and a framework would be overkill.

**The trade-off (be honest about it):** for a big app with many pages, login and lots of user actions, plain JavaScript gets messy and a framework like React becomes worth it. HavenRL isn't that.

## 2. What the page shows

```
┌──────────────────────────────────────────────┐
│ Title + test period                          │
│ Period: [All (2023–24)] [2023] [2024]        │  ← buttons (section 6)
├──────────┬──────────┬──────────┬─────────────┤
│ End ₹    │ Return % │ Drawdown │ Sharpe      │  ← 4 number cards (for the chosen period)
│ agent vs baseline, plus "▲ Agent better" or  │

├──────────────────────────────────────────────┤

```

**What it tells you (the honest story):** the agent wins only on **drawdown** (3.42% vs 4.63%). The baseline wins on money, return and Sharpe because of the 2023–24 gold rally. In the chart, the lines stay together until about March 2024, then gold takes off and the baseline pulls ahead.

**Basket strip:** Mostly Gold 276 days (57%), Mostly Bond 160 days (33%), Mostly Liquid 45 days (9%). Hover a block to see its dates.

## 3. The code, piece by piece

| Piece | What it does | Example |
|---|---|---|
| `<style>` with `--agent`, `--gold`, … | all colours defined once, by role | dark mode just swaps these values |
| `order(path)` | asks the waiter for one menu item | `await order("/summary")` |
| `totalReturn`, `maxDrawdown`, `sharpeRatio`, `countSwitches` | the report card in JavaScript, the **same formulas** as `metrics.py` | see section 6 |
| `periodRange(period)` | finds which days belong to a period | "2024" → from 2023-12-29 to 2024-12-31 |
| `showPeriod(period)` | runs when you click a button: cuts out those days, restarts both at ₹1,00,000, then redraws everything | click "2023" |
| `showCards(agent, baseline)` | works out the 4 scores and decides who wins each | drawdown: **lower** is better, so the agent wins with 3.42 < 4.63 |
| `showValueChart(dates, agent, baseline)` | draws the line chart the first time; after that it only **swaps the numbers** (`chart.update()`) | hover anywhere to see both values for that day |
| `showBasketStrip(dates, actions)` | draws the coloured strip | days in a row with the same basket are joined into one block: 481 days become about 103 blocks |
| `main()` | fetches the data once, connects the buttons, shows "All"; if the API is down, shows an error message instead of a blank page | "Could not load data from the API. Is it running?" |

**The key idea (the "order"):**
```js
const res = await fetch("/summary");  // ask the waiter (sends GET /summary)
const data = await res.json();        // JSON text → JavaScript data
data.agent.final_value                // 116979.36 → shown as "₹1,16,979"
```
- **`fetch`** = JavaScript's way to send a request to an API.
- **`await`** = "wait for the answer before continuing" (the answer takes a moment to arrive, i.e. latency).

**A detail about the strip:** `agent_actions` has **481** items but `daily` has **482**. The basket chosen on day *i* is held until day *i+1*, and there's no choice to make after the last day. So `actions[i]` is drawn against `daily[i+1]`.

## 4. Design choices

- **Colours:** agent = blue, baseline = orange. Baskets: Gold = yellow-gold, Bond = green, Liquid = purple. The palette was checked with a colour-blindness validator, and it passes.
- **Colours are never alone:** every colour also has a text label (legend, "Agent better"), so colour-blind users can read it too.
- **Dark mode:** follows your computer's setting automatically, with its own colours picked for the dark background.
- **Animation off:** the chart draws instantly. (With animation on, a test screenshot caught the chart before the lines appeared.)

## 6. Period buttons: All / 2023 / 2024 (added 2026-10-18)

**Why:** to give the user something to **do** on the page (an input), not just something to look at. Clicking a year tells a story that the "All" view hides.

**What happens when you click "2024":**
1. `periodRange("2024")` picks the days of 2024, **plus the last day of 2023** (2023-12-29) as the starting point. Without it, the first day's move of 2024 would be lost. (Like measuring a runner's 2nd lap: you start the clock where lap 1 ended.)
2. **Rebase:** both lines restart at ₹1,00,000 on that starting day. Otherwise the agent (₹1,08,523) and the baseline (₹1,09,132) would start 2024 with different money and the comparison wouldn't be fair. Example: agent ₹1,08,523 → ₹1,17,000 becomes ₹1,00,000 → ₹1,07,811.
3. The 4 cards are worked out again **in the browser**, the chart swaps its numbers, and the strip shows only 2024.

**No new API call.** All 482 days were already loaded once by `/results`, so a click only slices that list. It's instant, with no waiting on the server (low latency, see NOTES_api.md).

**Why calculate in JavaScript and not ask the API?** Asking the API would need a new endpoint like `/summary?year=2024`. That's also a good design, and it's how V2's dynamic `/backtest` would work. For 3 fixed buttons on data we already have, the browser can do it instantly. The rule: **the browser may do small maths on data it has; the heavy work (training, running the agent) stays in Python.**

**Same formulas, checked:** the JavaScript versions of total return, max drawdown and Sharpe copy `metrics.py` exactly (Sharpe uses the same "population" std as numpy, ×√252). They were tested against Python for all 3 periods and every number matched.

**The results (each period starts at ₹1,00,000):**

| Period | Agent end | Baseline end | Agent return | Baseline return | Agent drawdown | Baseline drawdown | Agent Sharpe | Baseline Sharpe | Switches |
|---|---|---|---|---|---|---|---|---|---|
| All | ₹1,16,979 | ₹1,24,770 | 16.98% | 24.77% | **3.42%** | 4.63% | 1.48 | **1.65** | 102 |
| 2023 | ₹1,08,523 | ₹1,09,132 | 8.52% | 9.13% | **3.40%** | 4.12% | **1.68** | 1.50 | 48 |
| 2024 | ₹1,07,792 | ₹1,14,330 | 7.79% | 14.33% | **3.42%** | 4.63% | 1.31 | **1.78** | 54 |

**The story the buttons reveal:**
- **2023:** the agent nearly kept up on money (8.52% vs 9.13%), had a smaller fall, and **beat the baseline on Sharpe** (1.68 vs 1.50). It was the better *risk-adjusted* choice that year.
- **2024:** gold rallied hard. The baseline was always mostly in gold, so it won clearly (14.33% vs 7.79%).
- So the agent lost overall mainly because of **one year's gold rally**, not because it was bad every year. This is a good, honest point for an interview.

**Test (2026-10-18):** a browser test copy clicked "2024". The button turned dark, the info line said "246 trading days … switched basket 54 times", and the cards, chart and strip all showed only 2024 with the numbers above.
